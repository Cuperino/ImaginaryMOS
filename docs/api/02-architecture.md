# Architecture {#architecture}

[TOC]

The whole design exists to serve one goal: **one protocol implementation that
runs everywhere** — embedded devices, servers, and the browser — without
forking behavior per platform. This page explains the shape that makes that
possible. The authoritative source is
`reference/imaginarymos-implementation-plan.md`; this is the orientation.

## The sans-I/O rule {#arch_sansio}

Everything under `core/` is **free of I/O**. Nothing there opens a socket,
spawns a thread, reads a clock, or touches the filesystem. Side effects arrive
only through injected interfaces:

| Interface | Supplies | Required |
| --------- | -------- | -------- |
| @ref imos::ITransport | outbound frames + inbound delivery | yes |
| @ref imos::IClock | monotonic time (scheduling) + wall-clock (timestamps) | yes |
| @ref imos::IMessageStore | durable-before-send buffer + `messageID` dedupe | yes |
| @ref imos::IRandom | retry/reconnect jitter (never secrets) | optional |
| @ref imos::ILogger | diagnostics | optional |
| @ref imos::ITimerQueue | push-mode wakeups | optional |

This is the single most important invariant in the codebase, and it buys three
things at once:

- **Portability.** The WASM target has no threads and no blocking sockets; a
  sans-I/O core simply doesn't ask for them. The same source compiles for iOS
  and Android without `#ifdef` mazes.
- **Testability.** Inject a fake clock and a loopback transport and an entire
  reliability scenario — ack timeouts, retries, resync — runs deterministically
  in microseconds (see @ref gs_testing).
- **One place for protocol fixes.** A bug in the state machine is fixed once in
  `core/`; both role libraries inherit it.

Preserve it. If a change under `core/` wants a socket, a thread, or a clock, the
answer is a new injected interface, not a direct call.

## Layering {#arch_layering}

Dependencies flow in exactly one direction:

```
transports  →  framing  →  codec  →  session  →  role APIs (imos / incs)  →  app
```

with `IMessageStore`, dialect profiles, config, and logging cutting across. A
lower layer never reaches up.

- **transports/** — the concrete wires. The MOS 4.0 WebSocket client/server over
  IXWebSocket (`ws40_ixws`) and the browser client (`ws40_emscripten`). Legacy
  MOS 2.8 TCP and MOS 3.x SOAP transports are later milestones.
- **framing/** — the deframer that turns a byte stream into whole messages and
  tolerates coalesced frames.
- **codec/** — parse/serialize with three invariants: lossless retention of
  unknown subtrees (they ride through and re-serialize), opaque `mosPayload`
  (never re-normalized by default), and byte-clean round-trips of the spec
  examples. Per-message structs are **machine-generated** under `codec/gen/`
  (regenerated by `tools/codegen/gen_messages.py`, never hand-edited) and are
  excluded from this reference to keep it focused; the hand-written
  @ref imos::codec::Message model is the surface you build against.
- **session/** — @ref imos::PeerSession "imos::PeerSession": one per remote party, up to three
  channels, enforcing the reliability rules below.
- **role APIs** — @ref imos::Device and @ref incs::Ncs, thin compositions over
  one session plus the profile responders.

## The session model {#arch_session}

One @ref imos::PeerSession owns the relationship with one remote party across up
to **three channels**, mapping to the legacy MOS ports:

| Channel | Legacy port | Carries |
| ------- | ----------- | ------- |
| @ref imos::Channel "Mom" | 10540 | machine info, object messages (Profiles 0/1/3) |
| @ref imos::Channel "Ro"  | 10541 | running-order construction & control (Profiles 2/4/5/7) |
| @ref imos::Channel "Aux" | 10542 | object search (Profile 3) |

Each message type knows its own channel from the spec's per-message *Port*
annotation, so `enqueue()` routes automatically. Per channel, the session
enforces the spec §3.3 reliability rules:

- **in-flight-of-one** strictly sequential delivery, with the three channels
  mutually independent;
- **retry on ack timeout** with capped retries, then link-fault escalation;
- **durable-before-send** buffering through `IMessageStore`;
- inbound **`messageID` dedupe** so a peer's retransmit is idempotent;
- **heartbeat/keepAlive** on idle (never faster than the 30-second floor).

Two seams matter when reading the profile code:

- @ref imos::PeerSession::enqueueReply — a *terminal reply* (a `listMachInfo`
  answering `reqMachInfo`, a `mosObj` answering `mosReqObj`). It is sequenced
  but never awaits an ack of its own, and it bypasses the in-flight-of-one gate
  so crossing request/reply exchanges can't deadlock. Every profile responder
  uses it.
- @ref imos::PeerSession::postEvent — how the profile layer announces an
  application event (e.g. `ResyncNeeded`) through the session's queue without
  the session knowing what triggered it.

## Events out: the drain model {#arch_events}

Facades never call you back. Instead, results accumulate in queues that you
drain each loop:

- @ref imos::Device::nextEvent / @ref incs::Ncs::nextEvent — the catch-all
  @ref imos::SessionEvent stream: acks for your own sends, delivery failures,
  channel faults, duplicate suppressions, protocol/store errors, and Profile 6
  foreign-reference notices.
- **Per-profile drains** — higher-level, already-acked results:
  `nextDirectoryEvent()` (Profiles 1/3), `nextCtrlRequest()` / `nextItemCue()`
  (Profile 5), `nextItemReplaceResult()` (Profile 3), `nextStoryActionResult()`
  (Profile 7), and so on. Each profile guide lists its own.

Alternatively, you `attach()` a **sink** (@ref imos::profiles::IStorySink,
@ref imos::profiles::IControlSink, …) and the facade delivers to it during
`poll()` instead of queueing. Sinks and drains are mutually exclusive per
profile: attach a sink and its queue stays empty.

## Pull-mode integration {#arch_pullmode}

The library owns no threads by default. The host drives everything from its own
loop: push connectivity and frames in, call `poll()`, drain the queues. For
push-mode hosts that would rather sleep until work is due, `nextDeadline()`
reports the earliest instant `poll()` has timed work (a retry, a keepAlive, a
paced release), and the optional `ITimerQueue` lets the session request a
wakeup. The concrete loop is in @ref gs_loop.

## Encoding policy {#arch_encoding}

Internally everything is UTF-8. On the wire, the 4.0 default is **UCS-2
big-endian on binary WebSocket frames**; UTF-8 on text frames is a per-peer
option. The receive side **expects** the configured encoding rather than
sniffing it, so the `SessionConfig` encoding, the transport `wireEncoding`, and
the peer's actual encoding must all agree — a mismatch surfaces as a transport
protocol error, not a silent mojibake. UCS-2 cannot represent non-BMP code
points; the replace-or-reject policy for those is a per-dialect decision.

## Two roles, one core {#arch_roles}

@ref imos::Device is the primary product — embedded in MOS devices, pull-mode,
no library-owned threads. @ref incs::Ncs is its mirror over the identical core
and also powers the interoperability simulator. Because both are thin
compositions over the same @ref imos::PeerSession and the same profile
responders, a protocol fix lands once and both roles get it. The profile guides
always show **both** sides of each exchange for exactly this reason.
